# Эксплуатация

Что делать с уже работающей установкой: как следить, как чинить, как
обновлять и восстанавливаться.

---

## Быстрая проверка состояния

```bash
docker ps                                  # оба контейнера — Up (healthy)
docker logs NOISEFLOOR-amneziawg-panel --tail 30
curl -s http://127.0.0.1:8000/api/health   # без пароля: ok, interface_up, restarts
```

`(healthy)` у панели означает, что поднят сам туннель, а не только веб-
интерфейс: `/api/health` отвечает `503`, когда интерфейс `awg0` должен быть,
а его нет. Если он пропал (например, OOM-killer убил `amneziawg-go`), панель
поднимает его сама в течение полуминуты; счётчик `restarts` в ответе растёт —
значит, это уже случалось, и стоит посмотреть `dmesg -T | grep -i "out of
memory"` и добавить машине swap.

Дальше — через API панели. Токен получается один раз и живёт 12 часов:

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"ПАРОЛЬ"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
```

```bash
curl -s http://127.0.0.1:8000/api/status -H "Authorization: Bearer $TOKEN"
curl -s http://127.0.0.1:8000/api/server/cascade/status -H "Authorization: Bearer $TOKEN"
```

## Мониторинг

Оба сервиса отдают метрики в формате Prometheus:

- панель — `GET /api/status/metrics` (нужен Bearer-токен)
- релей — `GET /api/metrics` (Basic-авторизация)

```yaml
scrape_configs:
  - job_name: noisefloor-panel
    metrics_path: /api/status/metrics
    bearer_token: "ВАШ_ТОКЕН"
    static_configs:
      - targets: ["панель:8000"]
```

Что стоит выводить в алерты:

| Метрика | Когда тревожно |
|---|---|
| `noisefloor_interface_up` | `0` — VPN-сервер лежит |
| `noisefloor_interface_restarts_total` | растёт — интерфейс пропадает и его поднимает надзор; ищите OOM |
| `noisefloor_rules_ok` | `0` — правила фаервола не встали, текст ошибки в статусе панели |
| `noisefloor_rules_restored_total` | растёт — кто-то сносит правила снаружи (ufw, iptables -F, чужой скрипт) |
| `noisefloor_cascade_verified` | `0` при включённом каскаде — данные через него не идут |
| `noisefloor_cascade_restarts_total` | быстро растёт — каскад в цикле падений |
| `noisefloor_peers_online` | ноль дольше обычного |
| `noisefloor_relay_traffic_active` | `0` при живых клиентах |

`noisefloor_cascade_verified` — самая ценная из них. Она отвечает на вопрос
«идут ли данные», а не «запущен ли процесс», и именно её отсутствие когда-то
позволило проекту месяц не замечать неработающий каскад. Значение `-1`
означает, что проверки ещё не было (первая — примерно через полминуты после
старта).

## Резервные копии

Снимаются сами: при старте панели и дальше раз в сутки. Хранятся последние 14
в `data/backups/`.

База в архив попадает снимком через backup API SQLite и проверяется
`PRAGMA integrity_check`. Если проверка не прошла, архив не создаётся, а ошибка видна
на вкладке **Сервер** рядом с кнопкой и в `GET /api/backup/status`.

**Забрать копию:** в панели вкладка **Сервер** → **Скачать копию** (собирается
свежая на лету), либо:

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8000/api/backup/download -o backup.tar.gz
```

Пока панель работает без TLS, скачивать копию лучше через SSH-туннель, а не по
открытому HTTP — внутри архива приватные ключи всех клиентов.

**Восстановление:**

```bash
cd /opt/noisefloor-panel
docker compose down

# если копия зашифрована
openssl enc -d -aes-256-cbc -pbkdf2 -in backup.tar.gz.enc -out backup.tar.gz

tar xzf backup.tar.gz -C data/
docker compose up -d
```

Клиентам ничего перенастраивать не нужно: ключи те же.

**Чего копии не покрывают.** Они лежат на том же диске, что и оригинал. От
случайного `rm -rf` спасают, от потери сервера — нет. Увоз копии на другой
хост пока не автоматизирован; простейший вариант — забрать по SSH:

```bash
scp root@сервер:/opt/noisefloor-panel/data/backups/$(ssh root@сервер \
    'ls -t /opt/noisefloor-panel/data/backups | head -1') ./
```

## Уведомления

**Панель.** Вкладка **Сервер**, блок «Уведомления»: webhook, токен бота и ID чата
Telegram, кнопка «Тестовое сообщение». Webhook получает POST с JSON `{"text": "..."}`.

| Событие | Когда приходит |
|---|---|
| Канарейка упала или восстановилась | новое состояние держится 120 с |
| Переключение релея, все релеи недоступны | то же, только при двух и более релеях |
| Интерфейс перезапущен надзором, правила восстановлены | сразу |
| Отпечаток релея не совпал | сразу, проверка работает как раньше |
| Обновление установлено, откатилось или не удалось | после следующего запуска панели |
| Бэкап не удался, снова создаётся | сразу, опрос раз в 30 с |

По одному событию не чаще раза в 5 минут, всего не больше 20 сообщений в час:
`NOTIFY_MIN_INTERVAL_SECONDS`, `NOTIFY_MAX_PER_HOUR`, `NOTIFY_HOLD_SECONDS`,
`NOTIFY_INTERVAL_SECONDS` в `.env`. Разовое событие сверх лимита отбрасывается, а
следующее сообщение говорит, сколько пропущено.

Отправка идёт через каскад, при неудаче напрямую. Сервер с заблокированным Telegram и
лежащим каскадом отправить не сможет: сообщение ждёт в очереди (до 50), и на этот
случай есть уведомление от релея. Сообщение считается доставленным, если дошло хотя
бы по одному каналу. Токен лежит в `data/notify.json` с правами 600 и попадает в бэкап.

**Бот из скрипта.** Создайте бота у @BotFather, напишите ему `/start`, узнайте свой
`chat_id` (например, у @userinfobot). Новая установка, панель или релей:

```bash
export NOTIFY_TELEGRAM_TOKEN=123456:ABC-DEF
sudo -E bash install.sh --telegram-chat-id 123456789
```

На уже работающем сервере то же с `--telegram-only`: скрипт меняет в `.env` только эти
две строки и перезапускает контейнеры (`docker compose up -d`). Релей настраивать
необязательно. Токен лучше передавать через окружение: аргументы командной строки видны
в `ps` и попадают в историю. На панели значения из `.env` работают, пока бот не сохранён
в интерфейсе: сохранённое важнее, в том числе пустое значение.

**Релей.** Шлёт сообщение, если панель не приходила за параметрами дольше
`NOTIFY_PANEL_SILENT_MINUTES` (15). Настройки в `.env` релея: `NOTIFY_WEBHOOK_URL`,
`NOTIFY_TELEGRAM_TOKEN`, `NOTIFY_TELEGRAM_CHAT_ID`. По умолчанию выключено. Отсчёт
начинается с первого обращения панели после запуска релея, поэтому без настроенной
синхронизации сообщений не будет.

## Логи

```bash
# приложения
docker logs NOISEFLOOR-amneziawg-panel --tail 100
docker logs NOISEFLOOR-vless-reality --tail 100

# VPN-движок (лежат в data, переживают пересоздание контейнера)
tail -100 /opt/noisefloor-panel/data/cascade-xray.log
tail -100 /opt/noisefloor-relay/data/logs/xray-access.log
```

Логи движка ограничены по размеру и обрезаются на месте при переполнении:
полноценная ротация потребовала бы перезапуска xray, то есть разрыва всех
клиентских соединений ради уборки логов. Это журнал последнего инцидента, а
не архив за всё время.

Docker-логи ограничены в `docker-compose.yml` (10 МБ × 3). Если поднимаете
сервис своим compose — не забудьте про этот блок, без него json-лог растёт
бесконечно.

## fail2ban: перебор паролей SSH

Отдельный контейнер `NOISEFLOOR-fail2ban` в `/opt/noisefloor-fail2ban`,
ставится `fail2ban/install.sh`. Читает журнал sshd хоста (`/var/log/auth.log`,
а где его нет — журнал systemd) и банит адрес после 5 неудачных входов за
10 минут: на час, повторно — вдвое дольше, до недели. Баны лежат в своей
таблице nftables `inet f2b-table` и правила Docker, панели и zapret не
трогают. Сеть клиентов VPN (10.13.0.0/16) и адрес, с которого запускали
установщик, не банятся никогда.

```bash
docker exec NOISEFLOOR-fail2ban fail2ban-client status sshd            # кто в бане
docker exec NOISEFLOOR-fail2ban fail2ban-client set sshd unbanip АДРЕС # разбанить
docker logs NOISEFLOOR-fail2ban --tail 50
nft list table inet f2b-table                                           # сами правила
```

Настройки — `.env` рядом с `docker-compose.yml` (`SSH_PORT`, `MAXRETRY`,
`FINDTIME`, `BANTIME`, `IGNOREIP`), после правки `docker compose up -d`.
Обновление — `docker compose pull && docker compose up -d` в том же
каталоге; `noisefloor update` этот сервис не обновляет.

Заперли себя (вход по паролю с другого адреса): зайдите через консоль
хостинга или через туннель VPN — его сеть в исключениях — и разбаньте адрес.

## Канарейка

`cascade.verify()` ходит через loopback и не видит awg0, iptables, TPROXY и MTU.
Контейнер `canary` - настоящий AWG-клиент в своём сетевом пространстве, с одной
привилегией `NET_ADMIN`. Панель заводит для него служебного пира (в списке
клиентов его нет) и кладёт настройки в `data/canary/`, контейнер пишет туда
результат.

Раз в 60 секунд через туннель:

1. есть рукопожатие с сервером;
2. DNS-сервер клиентов отвечает на запросы `CANARY_DNS_NAMES`;
3. адрес выхода из `CANARY_TRACE_URL` совпадает с адресом релея;
4. `CANARY_DOWNLOAD_URL` скачивается за `CANARY_MAX_DOWNLOAD_SECONDS` со скоростью
   не ниже `CANARY_MIN_SPEED_BPS`.

Результат: строка «Канарейка» на вкладке каскада, `canary_*` в
`/api/server/cascade/status`, метрики `noisefloor_canary_ok`,
`noisefloor_canary_duration_seconds`, `noisefloor_canary_speed_bytes_per_second`.
`canary_stage` показывает, на чём проба упала: `handshake`, `dns`, `exit_ip`,
`download`, `tunnel`, `stale` (контейнер молчит дольше 3 минут).

Что важно знать:

- Канарейка работает только при включённом каскаде.
- Скачивание стоит примерно 1,4 ГБ трафика релея в сутки. Интервал меняется через
  `CANARY_INTERVAL_SECONDS` в окружении контейнера.
- Ответ 429 от сайта со скачиванием не считается поломкой: проба остаётся
  успешной, а скорость не измеряется.
- Контейнер стучится в сервер через шлюз bridge-сети, поэтому внешняя часть пути
  (клиент - сервер) канарейкой не проверяется. Проверяются awg0, правила, xray и
  участок до релея.
- На существующей установке контейнера нет: он появляется, если добавить сервис
  `canary` из `amneziawg-panel/docker-compose.yml` в свой compose.

## Самопроверка релея

Раз в 2 минуты релей поднимает временный xray-клиент, подключается к своему
входу по REALITY и запрашивает `generate_204`. Результат - поле `selfcheck` в
`/api/health` и подробности с текстом ошибки в `/api/status` (под паролем).

| `selfcheck` | Значение | `/api/health` |
|---|---|---|
| `pending` | первый результат ещё не получен | 503 |
| `ok` | клиент прошёл | 200 |
| `failed` | две неудачи подряд, при этом напрямую наружу выходит | 503 |
| `unknown` | наружу нет выхода и напрямую, релиз тут ни при чём | 200 |
| `off` | `SELFCHECK_INTERVAL_SECONDS=0` | 200 |

После неудачи проверка повторяется через 20 секунд, одиночный сбой здоровья не
отнимает. Сам по себе `503` ни к чему не приводит: контейнер становится
`unhealthy`, а откат делает только агент сразу после обновления. Ещё `failed`
бывает при недоступном `dest`: xray обращается к нему при каждом подключении.

Каждая проверка - короткий запуск второго процесса xray. Если на маленькой VPS
это мешает, увеличьте `SELFCHECK_INTERVAL_SECONDS` (в установках старше этой
версии переменную надо дописать в `environment` файла compose). Подключения с
`127.0.0.1` не считаются клиентами, но их байты входят в общий счётчик трафика.

## Диагностика каскада

Каскад — самая сложная часть, и ломается он чаще остального.

**Шаг 1. Что говорит сама панель.**

```bash
curl -s http://127.0.0.1:8000/api/server/cascade/status -H "Authorization: Bearer $TOKEN"
```

- `enabled: false` — каскад просто выключен в настройках;
- `configured: false` — не задана ссылка `vless://`;
- `running: false` — процесс не поднялся, смотрите `error`;
- `verified_ok: false` — процесс жив, но данные не идут; причина в
  `verify_error`;
- `restarts` растёт — процесс падает и поднимается по кругу.

**Шаг 1а. Если настроена синхронизация.** Поля `sync_error` и `synced_at` в
том же ответе говорят, удаётся ли панели вообще спросить релей. Частое:
неверный токен (его меняли на релее), закрытый фаерволом порт панели релея,
опечатка в адресе. Форсировать проверку:

```bash
curl -s -X POST http://127.0.0.1:8000/api/server/cascade/sync \
    -H "Authorization: Bearer $TOKEN"
```

**Шаг 2. Логи движка.**

```bash
tail -50 /opt/noisefloor-panel/data/cascade-xray.log
```

Строка `REALITY: processed invalid connection ... handshake did not complete
successfully` на стороне релея означает камуфляжный домен с багом — см. ниже.

**Шаг 3. Правила перехвата на месте?**

```bash
iptables -t mangle -S NOISEFLOOR-TPROXY
ip rule list | grep 100
```

Должны быть два правила TPROXY (tcp и udp) и одно `ip rule` с меткой. Если
пусто — переприменените конфиг: панель → **Сервер** → **Применить на сервере**.

**Шаг 3а. Ядро умеет TPROXY?** Симптом: клиент подключён, рукопожатия идут,
DNS резолвится — но не открывается ни один сайт, а в счётчиках пира огромный
`rx` при почти нулевом `tx`. Загляните в лог движка:

```bash
grep IP_TRANSPARENT /opt/noisefloor-panel/data/cascade-xray.log
```

Строка `failed to set IP_TRANSPARENT > operation not supported` означает, что
xray не смог сделать TCP-слушателя прозрачным, и ядро дропает каждый пакет
клиентского TCP ещё до xray. UDP при этом работает — отсюда и обманчивая
картина с живым DNS. Наблюдалось на ядре `5.15`; на `6.x` и новее тот же образ
работает. Панель показывает это в ошибке каскада (`error` в статусе). Лечится
обновлением ядра:

```bash
apt install linux-generic-hwe-22.04 && reboot
```

— либо переходом на `redirect` (следующий шаг).

**Шаг 4. Откат на старый режим перехвата.** Если после перехода на TPROXY у
клиентов что-то ведёт себя странно — или ядро не тянет TPROXY, — вернуть
прежнее поведение можно одной переменной (только TCP, UDP пойдёт напрямую):

```bash
sed -i '/^CASCADE_INTERCEPT_MODE=/d' /opt/noisefloor-panel/.env
echo 'CASCADE_INTERCEPT_MODE=redirect' >> /opt/noisefloor-panel/.env
cd /opt/noisefloor-panel && docker compose up -d   # именно up -d: restart берёт старое окружение
# затем в панели: Сервер → Перезапустить интерфейс
```

Переключать нужно именно переменной: от неё зависят не только правила
iptables, но и конфиг движка. Вход каскада получает `sockopt.tproxy` только в
режиме `tproxy`; если оставить этот флаг при перехвате через nat REDIRECT,
xray примет соединение, определит «исходный» адрес назначения как самого себя
и оборвёт его с `loopback connection detected` в логе.

### Не работают звонки Telegram / WhatsApp, а сайты и сообщения — да

Почти всегда это режим `redirect`: в каскад заворачивается только TCP, а медиа
звонков идёт по UDP и выходит с адреса самого сервера. Если сервер в РФ,
звонки режутся — сообщения (TCP) при этом ходят через релей нормально.
Панель показывает это строкой «UDP идёт мимо каскада» в блоке «Каскад».

```bash
uname -r                                                  # 5.x — tproxy недоступен
grep CASCADE_INTERCEPT_MODE /opt/noisefloor-panel/.env    # auto | tproxy | redirect
docker exec NOISEFLOOR-amneziawg-panel iptables-save -t mangle | grep -c TPROXY   # 0 = redirect
```

Лечение — ядро 6.x и режим `auto` (или `tproxy`):

```bash
apt install linux-generic-hwe-22.04
sed -i 's/^CASCADE_INTERCEPT_MODE=.*/CASCADE_INTERCEPT_MODE=auto/' /opt/noisefloor-panel/.env
reboot
# после загрузки — обязательно пересоздать контейнер, иначе останется старый .env:
cd /opt/noisefloor-panel && docker compose up -d
```

Проверка: в mangle есть цепочка `NOISEFLOOR-TPROXY` с правилами `-p udp`, в
`data/cascade-xray.log` нет `IP_TRANSPARENT`, а
`conntrack -L -p udp | grep src=10.13.` не показывает прямых потоков клиентов
наружу (UDP теперь уходит через xray внутри TCP-соединения к релею).

## Несколько релеев

Резервные релеи добавляются в панели, раздел «Каскад» -> «Резервные релеи», или
через `POST /api/server/cascade/relays`. У каждого свой адрес, токен и
запомненный отпечаток сертификата. Смена адреса резервного релея - удалить и
добавить заново, отпечаток запомнится при первом опросе.

С одним релеем и настройкой «Не выпускать» конфиг xray такой же, как раньше. Со
вторым релеем или настройкой «Выпускать» появляются `burstObservatory` и
балансировщик `leastPing`. Каждый релей получает пробу раз в 10 секунд, это 8640
подключений в сутки на релей. Адрес пробы задаёт `CASCADE_PROBE_URL`, ответ
должен быть 204.

Переключение касается только новых соединений. Те, что шли через умерший релей,
обрываются, и приложения открывают их заново.

«Если все релеи недоступны»:

| Настройка | Xray жив, релеи мертвы | Xray не работает |
|---|---|---|
| `block` (по умолчанию) | соединения идут в основной релей и не устанавливаются | перехват остаётся, трафик клиентов отбрасывается |
| `direct` | выход с адреса панели | перехват снимается до возврата xray |

При `direct` выход с адреса панели также случается первые секунды после каждого
запуска xray, пока не прошли первые пробы. Он же случится, если адрес пробы
недоступен со всех релеев, хотя сами они исправны. Канарейка в этих случаях
покраснеет на `exit_ip`: это ожидаемо, адрес выхода не адрес релея.

Упавший xray сторож перезапускает с паузами 1, 2, 5, 10, 20, 40 и 60 секунд, счёт
обнуляется после минуты работы. Какой релей выбран сейчас:

```bash
docker exec amneziawg-panel xray api bi -server=127.0.0.1:10086 relays
```

Откат панели на версию без этой функции безопасен: основной релей остаётся в
столбцах `server_config`, резервные старая версия не увидит. После возврата на
новую версию столбцы перекрывают запись основного релея.

## UDP и DNS через каскад

`CASCADE_XUDP=true` в `.env` панели, по умолчанию выключено. UDP идёт через XUDP
одним соединением к релею, а не отдельным соединением на каждый порт источника. TCP
остаётся без mux. DNS клиентов отвечает панель: кэш на сроки из ответов, промахи идут
через каскад к первому адресу из настройки DNS.

- UDP/443 (QUIC) отклоняется, браузер вернётся на TCP.
- В режиме `redirect` кэш работает только с `CASCADE_DNS_VIA_CASCADE=true`.
- Смена SNI заменяет исходящий: соединение XUDP обрывается, UDP-потоки поднимаются
  заново при следующем пакете.
- Смена настройки нужна с перезапуском панели, и она рвёт соединения клиентов.

## Запасной вход VLESS

Для сетей, где режут UDP. Вкладка **Сервер**, блок «Запасной вход VLESS»: включить,
выбрать порт, добавить клиента, отдать ссылку или QR-код. Клиенту нужно приложение с
поддержкой VLESS+REALITY (v2rayNG, Hiddify, Streisand и подобные). По умолчанию
выключено. Порт открыт, только когда вход включён, есть включённые клиенты и работает
каскад. Порт TCP нужно открыть в фаерволе хостинга.

- **Трафик** идёт только через релей. Разделение маршрутов на него не действует. Настройка
  «Если все релеи недоступны» тоже: даже при «напрямую» с адреса сервера он не выходит.
- **Частные адреса** (`127.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10` и другие) и `localhost`
  закрыты: вход смотрит в интернет.
- **Занятый порт** каскад не роняет: xray запускается без входа, а в интерфейсе и в
  `cascade_last_error` появляется предупреждение. Ту же проверку проходит каждый запуск.
- **Любое изменение** (настройки, новый или выключенный клиент) перезапускает xray и рвёт
  соединения клиентов каскада. Лучше делать это, когда сеть не занята.
- **Камуфляжный сайт** обязан отвечать на TLS 1.3 с этого сервера: через него проходит
  рукопожатие REALITY. Если он недоступен из страны сервера, вход работать не будет.
  Значение по умолчанию `dl.google.com:443` нужно проверить на своём хостинге.
- **Версия клиента:** xray 26.7.28 по умолчанию принимает на REALITY клиентов с Xray-core
  не старше v26.3.27 и пишет об этом в журнал при запуске. Приложение на старом ядре
  получит отказ, его нужно обновить.
- **Адрес в ссылке** берётся из `endpoint_host`, того же поля, что у конфигов AmneziaWG.
- **Ключи** новые при первом включении и не меняются. Сменить ключ можно только удалением
  строки `fallback_config` из базы, и все ссылки придётся выдать заново.

## MTU

Если MTU в настройках не задан, панель считает его из профиля: `1424 − S4`, и пишет
в конфиг сервера и клиентов. Явное значение важнее. Клиент со старым конфигом
(1420 или без строки MTU) может фрагментироваться при S4 больше 20: раздайте новые
конфиги. На AmneziaWG 1.x и WireGuard расчёт не влияет, S4 у них нет.

Проверка во время загрузки, любая строка означает фрагментацию:

```bash
tcpdump -ni <egress> 'udp port <awg-port> and ip[6:2] & 0x3fff != 0'
```

## IPv6 клиентов

Наружу IPv6 клиентов не выходит: `::/0` остаётся в конфиге, чтобы такой трафик не
пошёл мимо туннеля. Чтобы приложения не ждали таймаута, клиент получает внутренний
адрес `fdXX:...` (ULA, выводится из ключа сервера), а сервер сразу отказывает: TCP
получает RST, остальное `icmp6-adm-prohibited`.

- Глобальная пересылка IPv6 не включается: `net.ipv6.conf.all.forwarding=1` отключил
  бы приём RA, и VPS на SLAAC потерял бы собственный IPv6. Пакеты с туннеля локальным
  маршрутом попадают в `INPUT`, где их отклоняет цепочка `NOISEFLOOR-V6`.
- Служит только для отказа: связи между клиентами и с сервером по ULA нет.
- Клиентам со старым конфигом ничего не меняется, для быстрого отказа нужны новые.
- `CLIENT_IPV6_REJECT=false` выключает всё. Панель выключает это сама, если на хосте
  отключён IPv6, нет `ip6tables` или MTU меньше 1280. Смена настройки требует
  перезапуска панели.

Проверка с клиента, отказ должен прийти сразу:

```bash
curl -6 --connect-timeout 5 https://ipv6.google.com
```

## Ротация SNI без обрывов

При включённой ротации на релее работает nginx: `127.0.0.1:18443` (`SNI_ROUTER_PORT`),
конфиг `/data/sni-router.conf`. Проверить, что он жив и выбирает хост:

```bash
docker exec vless-reality cat /data/sni-router.conf
curl -kv --resolve dl.google.com:18443:127.0.0.1 https://dl.google.com:18443/ 2>&1 | grep subject
```

Если nginx не поднимается, сторож вернёт прямой `dest`: релей работает, но каждая
ротация снова перезапускает xray. Ошибка видна в `router_error` в `/api/status`.

Панель меняет исходящий на ходу, только если других отличий в конфиге нет. Иначе
xray перезапускается, как раньше.

## Разделение маршрутов: российские адреса мимо каскада

Галочка в настройках сервера («Российские адреса — напрямую»). Пока она
выключена, весь клиентский TCP идёт через каскад — как и раньше.

Что происходит при включении: движок сверяет адрес назначения с базой
`geoip.dat` и российские адреса выпускает наружу с адреса самого сервера,
минуя релей. Остальное продолжает уходить в каскад. Российские сайты
открываются в два-три раза быстрее (нет двух лишних хопов через релей), а
те, что не пускают зарубежные адреса, наконец работают.

**Плата:** такие сайты видят настоящий адрес этого сервера, а не адрес
релея. Это осознанный размен, поэтому по умолчанию выключено.

Как убедиться, что работает — с клиента, подключённого к туннелю:

```bash
curl https://api.ipify.org                     # ждём адрес РЕЛЕЯ
curl https://yandex.ru/internet/api/v0/ip      # ждём адрес ЭТОГО сервера
```

Если оба показывают адрес релея — смотрите ошибку каскада в панели: скорее
всего в образе нет базы geoip, и панель об этом пишет прямо.

Посмотреть решения движка по конкретным адресам (лог соединений выключен,
поэтому нужен отдельный запуск — рабочий процесс он не трогает):

```bash
docker exec NOISEFLOOR-amneziawg-panel sh -c '
  sed "s/\"access\": \"none\"/\"access\": \"\/tmp\/acc.log\"/" \
      /opt/panel/data/cascade-xray-config.json > /tmp/dbg.json'
# дальше запустить второй экземпляр на других портах и смотреть /tmp/acc.log
```

В строке будет видно `[cascade-in -> direct]` или `[cascade-in -> cascade-out]`.

**Российский сайт не открывается при включённом разделении.** Значит, он не
пускает адрес этого сервера (так ведут себя некоторые госсервисы и банки с
хостинговыми диапазонами) или лежит. До появления таблицы исключений лечится
выключением галочки; сама таблица — следующий этап.

**Правила меняет только панель.** `xray api adrules` заменяет весь набор
разом, поэтому руками в него лезть нельзя: следующее сохранение настроек
всё равно перезапишет.

## «Медленно и иногда не открывается»

Жалоба почти всегда общая, а причин бывает три, и различаются они замерами,
а не догадками. Мерить нужно по очереди, от дальнего конца к ближнему.

**1. Сколько тянет сам релей.** Он — потолок для всей связки: быстрее его
собственного канала каскад не поедет никогда.

```bash
# на релее
curl -o /dev/null -w '%{speed_download}\n' --max-time 30 http://cachefly.cachefly.net/100mb.test
```

**2. Сколько доезжает через каскад.** С панели, через её же пробный вход —
это ровно тот путь, которым идёт клиентский TCP:

```bash
docker exec NOISEFLOOR-amneziawg-panel \
  curl -o /dev/null -w '%{speed_download}\n' --max-time 30 \
  --proxy socks5h://127.0.0.1:10087 http://cachefly.cachefly.net/100mb.test
```

Здоровая связка отдаёт около 90% от первого замера. Если заметно меньше —
смотрите congestion control: на длинном плече `cubic` обваливает окно от
каждой потери, и разница с `bbr` доходит до полутора раз.

```bash
sysctl net.ipv4.tcp_congestion_control net.core.default_qdisc   # ждём bbr / fq
```

**3. Потери на самом сервере.** Ровные «иногда не открывается» при нормальной
скорости — это почти всегда переполнение таблицы conntrack: на гигабайте
памяти ядро берёт около 7 тысяч записей, а десяток активных клиентов их
выбирает.

```bash
conntrack -S | head -1      # insert_failed и drop должны стоять на месте
sysctl net.netfilter.nf_conntrack_max net.netfilter.nf_conntrack_count
```

Ненулевой и растущий `insert_failed` = молча потерянные пакеты. Лечится
`/etc/sysctl.d/99-noisefloor.conf` — его кладёт установщик; если сервер
ставили руками, файла может не быть.

Отдельно: пока включён каскад, QUIC (UDP/443) клиентам закрыт
(`CASCADE_BLOCK_QUIC=true`). В режиме `redirect` он ушёл бы мимо каскада с
настоящим адресом сервера. В режиме `tproxy` он едет через каскад поверх
TCP-туннеля до релея, и страницы в браузере грузятся в разы медленнее, чем
по TCP, а иногда встают до таймаута; Telegram и curl при этом работают
нормально — это и есть примета. Если клиент жалуется на медленные сайты
или видео, проверьте, что правило на месте:

```bash
iptables -L NOISEFLOOR-FWD -n -v | grep REJECT
# в tproxy ещё и исключение из перехвата, иначе до REJECT пакет не дойдёт:
iptables -t mangle -S NOISEFLOOR-TPROXY | grep "dport 443 -j RETURN"
```

**Не ставьте `www.microsoft.com` камуфляжным доменом.**

Часть его серверов отдаёт TLS-сертификат размером больше, чем принимает

## Обновление

Ничего не обновляется само по себе. Это сознательное решение: раньше сервер
раз в сутки собирал свежую версию из исходников и передёргивал интерфейс без
предупреждения. Обновление — это перезапуск панели вместе с интерфейсом
туннеля: клиенты отваливаются секунд на десять и переподключаются сами.
Поэтому момент выбирает человек, а не таймер.

**Как узнать, что вышла новая версия.** Панель и релей проверяют сами, раз
в шесть часов, и показывают плашку «Доступно обновление» — с заметками к
релизу и ссылкой (у релея — блок «Версия и обновления» на странице статуса). Что считать новой версией, задаёт `UPDATE_CHANNEL` в `.env`:
`stable` (по умолчанию) — релизы GitHub, то есть плашка появляется, когда
автор сознательно поставил тег; `latest` — каждый коммит в master. Блок
«Версия и обновления» на вкладке «Сервер» показывает текущую версию, версии
зашитых компонентов и версию релея — если узлы разъехались, там же будет
написано.

**Как обновиться.** Два равноценных пути — они делают одно и то же:

- кнопка **«Обновить сейчас»** в панели или на странице релея;
- на сервере: `noisefloor update` (обновляет всё, что есть на этом хосте;
  `noisefloor update relay` — только релей).

Что происходит в обоих случаях: прежний образ закрепляется тегом `:previous`,
скачивается новый, контейнер останавливается, `data/` копируется в
`data.pre-<версия>/` рядом с ней, контейнер поднимается на новом образе, агент
ждёт до двух с половиной минут, пока Docker не сочтёт его здоровым. Если канарейка
была зелёной до обновления, она должна позеленеть после, не позже чем через пять
минут (`NOISEFLOOR_CANARY_TIMEOUT`, секунды). Что-то не дождался - останавливает
контейнер, возвращает копию данных и прежний образ и пишет об этом в панель
(«последнее обновление не удалось, возвращена прежняя версия»). Никаких состояний
«полуобновился и лёг».

Хранятся две последние копии. В них база и ключи без шифрования, с теми же правами,
что в `data/`. Логов, бэкапов и каталога канарейки в копии нет, откат их не трогает.
Если данные скопировать не удалось (например, кончилось место), обновление
отменяется и работает прежняя версия.

Ещё команды на сервере:

```bash
noisefloor status      # версии и здоровье сервисов на этом хосте
noisefloor check       # есть ли что-то новее в реестре и какой последний релиз
noisefloor rollback    # вернуть :previous и данные на момент обновления руками —
                       # например, если новая версия поднялась, но вам не
                       # нравится. Клиенты, заведённые после обновления, пропадут
                       # из работающей базы, данные до отката лежат
                       # в data.before-rollback/
```

Кнопке нужен агент на хосте — systemd-юнит, который ждёт запроса от
панели или релея (агент один, обслуживает оба сервиса, обновляет только
того, кто попросил). Установщики ставят его сами; если сервис ставили
вручную:

```bash
curl -fsSL https://raw.githubusercontent.com/vbif666/noisefloor/master/tools/noisefloor \
    -o /usr/local/bin/noisefloor && chmod +x /usr/local/bin/noisefloor
mkdir -p /etc/noisefloor
echo "panel=/opt/noisefloor-panel" >> /etc/noisefloor/services   # что стоит на этом хосте
echo "relay=/opt/noisefloor-relay" >> /etc/noisefloor/services   # (одна строка или обе)
noisefloor install-agent
```

Без агента сервис всё равно покажет, что обновление есть, и подскажет
команду; кнопки не будет. Если агент ставили до версии 1.0.3 (он тогда
следил только за панелью) — выполните `noisefloor install-agent` ещё раз
после обновления команды.

**Почему сервисы не обновляют себя сами.** Для этого нужен `docker.sock`,
а это root на хосте у веб-приложения, открытого в интернет. Вместо этого
сервис кладёт файл-запрос в свой каталог данных, а хостовый агент делает
остальное. Файлы, через которые они разговаривают, лежат в `data/`:
`update-request.json` (запрос), `update-result.json` (что вышло),
`agent.json` (агент установлен).

**Про `:previous` и место на диске.** Один лишний образ (~300 МБ) — цена
того, что откат вообще возможен. Закрепляется он именно тегом: в новом
хранилище образов Docker (containerd, `docker info` → `driver-type:
io.containerd.snapshotter.v1`) образ без тега удаляется сборщиком мусора
сразу, даже пока из него работает контейнер. Это выяснилось при проверке
отката на живом сервере — по ID откатывать было уже не к чему.

**По старинке** всё ещё работает, просто без страховки:

```bash
cd /opt/noisefloor-panel && docker compose pull && docker compose up -d
```

Правила фаервола при пересоздании контейнера не дублируются — они живут в
отдельных цепочках, которые очищаются перед заполнением. Проверить:

```bash
iptables -S FORWARD | grep -c NOISEFLOOR      # должно быть 1
iptables -t nat -S POSTROUTING | grep -c NOISEFLOOR   # 1
```

Если больше единицы — вы на старой версии, где правила накапливались.

## Синхронизация параметров с релеем

Если в блоке «Каскад» заданы адрес релея и токен, панель раз в пять минут
спрашивает у релея его текущие параметры и обновляет ссылку `vless://` сама.
Ссылка хранится на сервере и в интерфейсе не показывается — в ней лежит UUID,
то есть готовый доступ к релею. В панели видна только безопасная сводка:
адрес, порт, sni и метка.

Посмотреть саму ссылку, если это действительно нужно:

```bash
curl -s http://127.0.0.1:8000/api/server -H "Authorization: Bearer $TOKEN" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["cascade_vless_url"])'
```

Что это даёт: смена SNI или camouflage dest на релее больше не ломает каскад.
Раньше обе стороны после такой правки выглядели исправными, а трафик не шёл,
пока кто-нибудь не обновит ссылку вручную.

Обновление ссылки перезапускает только каскадный xray — туннель клиентов не
трогается, разрыва связи нет.

**Смена токена.** На панели релея есть кнопка «Сменить». Прежний токен
перестаёт работать сразу, поэтому новый нужно тут же вписать в панель, иначе
синхронизация встанет с ошибкой (сам каскад продолжит работать на последней
полученной ссылке).

## Ротация маскировки на релее

Блок «Ротация маскировки» на странице релея. Включается галочкой; интервал в
часах (по умолчанию 4) и пул хостов — по одному в строке. Следующий хост
выбирается случайно из пула, не совпадает с текущим и **объявляется заранее**:
момент и хост видны в заголовке блока и в ответе `/api/sync`.

Перед каждой сменой хост проверяется с самого релея: TLS 1.3, `h2` в ALPN,
цепочка сертификатов короче лимита REALITY (ловушка `www.microsoft.com` выше —
именно её эта проверка ловит) и рукопожатие до хоста не дольше
`DEST_MAX_HANDSHAKE_MS` (50 мс) — релей повторяет этот поход на каждое
соединение клиента, далёкий хост замедляет всех (см. ARCHITECTURE, «Задержка
camouflage-домена»). Не прошедший пропускается, причина попадает в журнал под
формой. Кнопка «Проверить пул» прогоняет ту же проверку по всем хостам сразу и
показывает миллисекунды — так видно заранее, кто отвалится и кто далеко.

**Если через каскад часть запросов висит по 8–12 с, а потом отваливается** —
проверьте порт релея: только 443 (ARCHITECTURE, «Порт релея — только 443»).
Быстрая диагностика с первого сервера: 100 запросов через socks-пробу,
`curl --socks5-hostname 127.0.0.1:10087 http://<релей>:8001/` — на 8443
несколько из них уйдут в таймаут, на 443 не должно быть ни одного.

**Если через каскад «всё открывается с задержкой»** — первым делом
`POST /api/rotation/check` на релее (или кнопка «Проверить пул»): хосты с
`ms` под сотню и есть причина. Пул по умолчанию мерился из Амстердама; на
другом хостинге его нужно пересобрать под свою географию. «Сменить сейчас» — внеочередная
смена на случайный годный хост, безопасна в любой момент (см. ниже).

**Прежний SNI принимается ещё 15 минут после смены.** Он остаётся в
`serverNames` рядом с новым, и клиент, который ещё не узнал о смене (панель
первого сервера опрашивает релей раз в пять минут, а ручная смена не
объявляется заранее), продолжает работать при новом dest. Проверено на живом
xray: со старым SNI из списка — проходит, без него — нет. В обзоре на
странице релея под SNI видно, какие прежние имена ещё принимаются и до
какого времени; то же — в `/api/sync` (`accepted_snis`). Истёкшие имена
убираются из списка при следующей смене, а не отдельным перезапуском:
перезапуск xray рвёт соединения клиентов.

Что происходит с каскадом. Панель первого сервера узнаёт момент смены из
`/api/sync` и приходит за новыми параметрами через несколько секунд после
него, а не на очередном пятиминутном опросе. Пауза каскада при смене —
перезапуск двух xray, секунда-две. В блоке «Каскад» панели рядом со временем
последней синхронизации написано, когда релей сменит SNI в следующий раз.

Если релей лежал и проспал объявленный момент дольше двух минут, он не
переключается задним числом — объявляет новый момент. Панель к тому времени
уже вернулась к обычному опросу и подхватит его в пределах пяти минут.

Пул по умолчанию проверен с релея 2026-09-11 (все — TLS 1.3, h2, цепочки
2.3–4.8 КБ): `dl.google.com`, `gateway.icloud.com`, `www.samsung.com`,
`www.amd.com`, `www.cloudflare.com`, `www.mozilla.org`, `www.speedtest.net`,
`www.dell.com`, `www.lenovo.com`, `www.asus.com`. Проверены и отвергнуты за
отсутствие `h2`: `www.apple.com`, `www.adobe.com`, `www.intel.com`,
`www.oracle.com`, `store.steampowered.com`, `www.ibm.com`, `www.sony.com`;
`www.bose.com` — за TLS 1.2.

## Смена пароля администратора

Пока делается через `.env`, кнопки в интерфейсе ещё нет:

```bash
cd /opt/noisefloor-panel
sed -i 's/^ADMIN_PASSWORD=.*/ADMIN_PASSWORD=новый-пароль/' .env
docker compose up -d
```

После первого входа удалите файл со сгенерированным паролем — он лежит
открытым текстом:

```bash
rm /opt/noisefloor-panel/data/INITIAL_ADMIN_PASSWORD.txt
```

## Безопасность: что сейчас не закрыто

Честный список. Ничего из этого не мешает работе, но знать нужно.

**Панель открыта в интернет и работает без TLS.** Пароль уходит по сети
открытым текстом. Закрывается фаерволом плюс доступ через SSH-туннель — см.
`docs/DEPLOY.md`, раздел «Что важно сделать после установки».

**Служебный порт каскада (12345) закрыт** — правила пускают на него только
туннель и локалхост. Слушать `0.0.0.0` движок обязан (после `REDIRECT` адрес
назначения переписан на адрес туннельного интерфейса, а не на loopback),
поэтому раньше порт был виден снаружи: в логе это выглядело как поток
`loopback connection detected` от сканеров. Использовать его как прокси и
тогда было нельзя, но лишняя точка входа ни к чему.

**SSH по паролю.** Перебор паролей закрывает fail2ban (раздел выше), если
он установлен. Надёжнее вообще выключить вход по паролю
(`PasswordAuthentication no` в sshd), когда есть вход по ключу.

**Вход в панель блокируется по имени пользователя.** Пять неверных паролей
для `admin` закрывают вход на пять минут — в том числе вам. Ограничение по IP
пока не сделано.

**Токен нельзя отозвать досрочно.** Кнопка «Выйти» очищает браузер, но сам
токен остаётся действительным до истечения 12 часов.

**Клиенты изолированы друг от друга** — устройство в туннеле не достучится
до соседнего. Это поведение по умолчанию. Если вам наоборот нужен доступ
между своими машинами через тот же туннель, поставьте `ISOLATE_CLIENTS=false`
в `.env` и перезапустите интерфейс.
